# MiniMax 健康助手

健康助手通过全站右下角按钮打开，也会拦截原有健康助手入口，在当前页面展开对话框；直接访问 `/health/assistant` 会自动打开。沿用现有 ChatGPT 登录。打开窗口只读取站内健康摘要，不调用模型；提交问题时，服务器会将本次问题、对话历史和所选范围的健康摘要发送至 MiniMax，无需额外勾选确认。

## 对话与显示

- 对话以消息气泡连续展示，支持追问。关闭窗口后保留本页对话；刷新、离开页面或开启新对话后清空，不写入数据库、localStorage 或 sessionStorage。
- 每次请求最多携带最近 4 轮完整问答（8 条消息），历史 JSON 的 UTF-8 总长度不超过 32,000 字节；客户端按完整问答对裁剪，服务端独立校验。角色只允许交替的 user、assistant，拒绝 system、工具消息和未知字段。
- 仅服务器构建当前用户的健康资料，历史回复不作为个人事实来源。切换日期或分享资料范围会清空历史，并重新读取所选范围的摘要。
- 模型回复由服务端 Markdown 渲染，支持标题、强调、列表、表格、引用和代码块；禁用原始 HTML 与图片，只允许安全协议链接。用户问题以纯文本显示。回复的数据来源在新标签页打开，便于核对时保留当前对话。
- 预设“健康数据教练”系统提示词，优先简要结论、数据依据和可执行建议，要求引用日期及来源、明确记录缺口，并保留医疗建议和只读边界。提示词在 `lib/health-assistant-prompt.ts` 维护。

## 网站内配置

登录后，从健康助手页进入“AI 设置”（`/settings/ai`），填写 MiniMax API 密钥、区域和账号可用的模型。默认模型为 `MiniMax-M3`；中国区选择 `cn`，国际区选择 `global`，应与密钥所属平台匹配。

保存后立即生效，无需修改代码或重新部署。修改模型或区域时，密钥留空表示保留原密钥；网页不会显示已保存密钥的任何部分。每位登录用户的配置独立，健康助手只使用本人的已保存配置。

“测试连接”只向 MiniMax 发送固定测试文本，不读取健康数据，需要单独确认可能产生的 API 费用。测试使用当前已保存版本，修改配置后需要重新保存和测试。连接测试与健康助手共用请求额度。保存成功仅表示配置已存储，实际模型权限和可用性以连接测试及真实请求为准。

删除密钥后停止后续调用；清除操作保留版本标识，避免旧页面的过期保存请求重新写回密钥。删除不会撤销已经发送到 MiniMax 的请求。网页不将密钥写入浏览器持久存储，也不把服务器加密密文发回浏览器。

## 服务端加密配置

MiniMax 密钥使用 AES-256-GCM 加密后存入 D1，随机 IV 与认证数据将密文绑定到当前用户。服务器主密钥 `AI_SETTINGS_ENCRYPTION_KEY` 保存在 Sites 的 Secret 环境变量中，与数据库分离。Sites 发布流程为这个站点自动准备一次主密钥，后续部署必须保留它；更换或遗失主密钥会使旧密文无法解密，需要用户重新填写 API 密钥。

本地预览可在未跟踪的 `.dev.vars` 配置独立的、标准 base64 编码的 32 字节随机主密钥。不要复用生产主密钥或将任何密钥提交到源码、GitHub 或聊天。原先直接使用全站 `MINIMAX_API_KEY` 的方式不再用于健康助手；现在通过网站保存个人配置。

官方资料：[兼容接口与模型参数](https://platform.minimax.cn/docs/api-reference/text-openai-api)、[获取 API Key](https://platform.minimax.cn/docs/guides/quickstart-preparation)。模型使用权限与费用由 MiniMax 账号决定。

饮食页的“图片”入口沿用同一配置；M3 和 M3.1 Flash 可通过图片内容块识别餐食。仅在本人点击识别后发送本次压缩图片和补充说明，不读取或附带其他健康、饮食或财务记录。图片不保存在本站，结果核对后才进入饮食记录。此入口与文字解析、健康助手及连接测试共用应用请求额度；详见[照片识别](nutrition.md#照片识别)。

## 数据范围和行为

新回答收到后会以打字机效果逐字显示，保留 Markdown 排版；可点“立即显示”展开全文。长回答自动加速，展示时间最多约 12 秒。系统启用“减少动态效果”时直接显示全文。最小化窗口会保留输出进度，向上阅读时不会强制滚动到底部。

- 只读本人所选有效健康指标与可选饮食营养摘要。保留近 7、30、90、180 或 360 天预设，并支持自定历史起止日期；按北京时间包含两端，最多 360 天且不能晚于今天。1–30 天保留日值，31–180 天按连续 7 日分组，181–360 天按 14 日分组，保留实际覆盖日期与缺失情况；步数、活动、睡眠取有记录日均值，体重／去脂体重取组内最后记录，饮食取已记录合计。记录更正与隐藏状态沿用现有规则。
- 发给模型的内容只有问题、日期、所选日值或明确分组值、记录覆盖情况及来源引用编号。主动选择“参考我设置的目标”时另附所选指标的用户自定目标和当前启用且未过期的体重计划；同时分享饮食时另附当前每日热量与三项营养素目标；不解释为医学目标或实测值。不发送登录身份、邮箱、财务数据、健康记录 ID、原始健康样本、饮食名称、份量或备注。真实来源名称仅用于站内引用表。
- 缺失数据保留未知；饮食热量只代表已记录且填了热量的部分。活动能量不是全天总消耗，不能直接与摄入相减计算热量缺口。
- 回答、问题与对话历史不写入数据库、浏览器持久存储或应用日志。MiniMax 对请求的处理适用其服务条款，本站不承诺第三方不保留请求。
- 页面显示最终回答的 Markdown 排版，不执行模型输出，不暴露推理内容，也不提供修改记录的工具。
- 每位用户每分钟最多 3 次、北京时间每天最多 20 次模型请求。额度按请求尝试计数，失败请求也计数；不自动重试可能产生费用的请求。额度计数存储在 D1 的 `ai_usage_limits`，不含问题或健康数据。

## 验证

配置完成后，先保存，再点击“测试连接”验证账号及模型访问。失败时，页面会显示固定的中文原因，以及可用的 MiniMax 错误码、上游 HTTP 状态与追踪 ID；服务端仅记录这些安全诊断字段，不记录上游原始错误文案、请求、回答或密钥。订阅 Key 的余额、套餐额度、模型权限和限流错误分别提示，避免全部显示为通用 502。健康助手仅在提交问题后调用 MiniMax；打开窗口或切换日期范围只读取站内摘要。未保存 Key 时，健康助手入口与摘要预览仍可用，分析按钮不可用，不会生成示例回答冒充真实模型结果。

## 图表、证据与等候

健康图表的“询问这张图”只带入当前指标、具体起止日期与问题草稿，读取站内预览，不调用模型。图表、该入口和“导出此范围”使用同一组北京时间日期；导出文件名标明范围。助手也可独立展开“自定日期”，切换范围清空当前对话并重新读取预览。自定日期随对话范围标识一起校验，相同天数的其他区间不能沿用旧范围追问。体脂配对图暂不支持此入口；不会自动替换成其他指标。可在助手内单独选择健康指标、饮食与是否参考目标，实际共享内容会先展示。

来源编号包含具体日期。正文中已知编号由服务器映射到对应记录页；饮食按日定位，多日分组可展开逐日链接。不存在的编号保持普通文字，代码中的编号不生成链接。

勾选饮食摘要时还会参考用户标记的“当天记完”与餐次记录／未进食状态。它们不保证实际全天摄入或热量准确。热量、碳水化合物、蛋白质和脂肪分别提供已记录合计与已知／未知数量。日均比较仅采用已记完、至少有食物且对应字段无缺失的日期；长期分组按每项分别提供可比较天数、合计与均值，不同营养素的样本天数可不同，不能用部分记录的整组合计冒充全天均值。当前营养目标不带历史生效日，不据此判定历史日期达标。关闭饮食分享时，饮食记录、每日营养目标和这些状态都不会读取或发送；逐项来源依据、食物名称和备注仍不提供给模型。

等待时显示已等候秒数，最小化后继续等候；429 显示倒计时并保留问题，结束后由用户主动重试。窗口显示应用今日剩余调用次数，和供应商 Token Plan 余额是两个独立概念。读取余量不消耗额度，失败的模型请求仍按应用尝试次数计数。

睡眠页的入睡、起床与规律性分析使用实际睡眠区间，旧时长记录不推算时刻；它不会因查看图表而自动发送给模型。当前助手仍按所选范围提供原有日值／分组与经过校验的睡眠分期。更多使用边界见 [P2 功能说明](p2-features.md)。
